Access Grant Experience — v3 Redesign

The access grant is Manifold's product. Every other screen exists to support the moment where the user says "Claude can see this, not that." This document rethinks that moment from first principles.

Three problems with v2: (1) Email access is per-message in the reading pane — users actually think in bulk by domain/category. (2) The access grant is dispersed across 4 locations — sidebar checkboxes, scope review, email reading pane, email sidebar. (3) The grant moment doesn't feel like the main event — it feels like settings plumbing.

What's wrong with v2's access model

Problem 1: Email access is backwards P1
v2 puts email exceptions in the reading pane — you have to browse to a hidden email, read it, then click "Add to this session." This is a discovery-then-decide flow when users actually want a decide-then-use flow.
The real user mental model: "Give Claude all my work emails. Hide personal and financial." That's a bulk decision by domain or category, not a per-email reading decision.

Apple Photos analogy: When you grant "Selected Photos" access, Apple shows you a grid picker where you select in bulk. They don't make you open each photo in a viewer and click "Share this one."

The incentive: If granting access to a single email requires navigating to it, reading it, and clicking a button — users will just set sensitivity to "Open" to avoid the friction. That defeats the entire trust model.
Problem 2: Access is dispersed, not centralized P2
v2 puts access controls in 4 places: Files sidebar (persistent checkboxes), Home tab (scope review), Email reading pane ("Add to this session"), Email sidebar (sensitivity dropdown). The user must visit multiple locations to do the one thing the app exists for.
Cooper's "commensurate effort" cuts both ways: Yes, the grant should be a deliberate moment. But forcing the user to visit 4 different surfaces to configure one session isn't deliberate — it's scattered.

Krug: "Don't make me think" also means "don't make me remember where things are." There should be ONE place for the grant decision, not four.

The solution: The Session Scope Review should be the SINGLE surface where you configure everything — files AND emails — with enough depth to do it well. Persistent defaults stay in the Files sidebar but are clearly secondary.
Problem 3: The grant doesn't feel like the product P2
The scope review in v2 is an "expansion panel" — it expands under the session card. This framing makes it feel like a confirmation dialog, not the main event. It's squeezed into the Home tab's content area alongside stat pills and activity feeds.
Show me the incentive: If the scope review is visually subordinate to stat pills, users will treat it as a speed bump to click through. The UI should make it feel like the most important thing on screen — because it is.

Proposed fix: The scope review should either (a) take over the full content area as a dedicated view, or (b) be a prominent sheet/modal that demands attention. Not an expansion panel tucked under a card.

Session Scope Review v3 Proposed

A dedicated, tabbed scope review that handles both files and emails in one surface. Files use source-level toggles with satisfying on/off states. Emails use domain-level bulk selection with category chips — not per-email reading pane buttons. The footer shows a live scope summary that updates as you toggle things on and off.

What changed from v2:
• Emails are domain-level bulk selection — not per-email reading pane buttons. Users check/uncheck entire domains.
• Category chips (Work, Automated, Personal, Auto-hidden) let users reason about email access by type, not by individual messages.
• Auto-hidden domains are visible but disabled — checkboxes are grayed out with reason badges. Users see what's blocked and why, right in the selection flow.
• Tabbed inner UI (Files | Emails | Options) keeps everything in one surface. No scattering.
• Source toggles with included/excluded visual states — green background + left border when included. Satisfying to toggle.
• Live footer counts update as you toggle sources and domains on/off. The trust boundary is always visible.
• "Include all / Exclude all" bulk buttons for sources.
• Sensitivity picker is inline in the Emails tab, not buried in a sidebar dropdown.

During-Session Access Controls

Once a session is running, users occasionally need to adjust access — add a source they forgot, or grant an exception for a hidden email they discovered. This should be possible without restarting the session, but it should still feel deliberate.

Key insight: Per-email exceptions (adding a specific hidden email during a session) still make sense as a during-session escape hatch. But they're the exception, not the primary flow. The primary flow is bulk domain selection in the Scope Review.

"Modify scope" reopens the Scope Review with current session state, allowing live adjustments without session restart. Changes take effect immediately (no new grant — the existing grant is amended).

Design Principles for the Access Grant

1. The grant IS the product
Manifold doesn't manage files — Finder does that. It doesn't read emails — Mail does that. Manifold's only job is to control what AI agents can see. The scope review is not a settings page or a confirmation dialog. It's the primary interaction. It should get the most design attention, the most screen real estate, and the most satisfying interactions.
2. Users think in categories, not individual items
"Share my work stuff with Claude" is a category decision. "Share this specific email from Alex at 10:42 AM" is not how anyone thinks about access control. Domain-level grouping (all from @company.com) matches the mental model. Category chips (Work, Automated, Personal) match it even better. Per-item selection should exist as an escape hatch, not as the primary flow.

Precedent: Apple's "Selected Photos" doesn't show photos one at a time. Gmail's "select all in this category." Slack's channel-level notification controls, not per-message.
3. The toggle should feel satisfying
When you include a source, the entire row changes to a green-highlighted state with a left accent border. When you exclude it, it dims. This isn't decoration — it's the trust boundary becoming visible. The user should look at the scope review and instantly know: "green rows = Claude can see. Dim rows = Claude can't." No reading labels, no parsing checkboxes. Just color.

Precedent: Apple's Focus Mode — allowed apps are bright, silenced apps are dimmed. Apple's Screen Time — allowed categories are green, restricted are gray.
4. One surface, three tabs, zero scattering
Everything about the grant happens in the Scope Review: file access (tab 1), email access (tab 2), session options (tab 3). The footer's live count is always visible regardless of which tab you're on. During the session, "Modify scope" reopens the same surface with current state.

The Files sidebar still has persistent defaults (independent checkboxes) — those pre-populate the Scope Review. But the sidebar is where you SET defaults. The Scope Review is where you COMMIT the trust boundary. Different verbs, different surfaces, clear relationship.
5. Show the boundary, not the count
v2's scope review footer showed "225 files (1.2 GB) + 1,089 emails accessible." That's a summary. v3's footer shows three numbers that update live: files included, emails visible, emails auto-hidden. The red "auto-hidden" counter is the trust signal — it tells you the sensitivity filter is working. When you toggle a source on, you see the file count tick up in real time. That's feedback. That's the moment of satisfaction.

Second-order effect: If the numbers don't change when you toggle something, you know something is wrong. The live counter is also a debugging tool for the trust model.
