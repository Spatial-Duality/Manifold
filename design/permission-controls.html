AI Access Control — Design Patterns v2

Manifold's core promise is controlled, inspectable AI access. The permission model is the trust boundary — it must be instantly legible, impossible to misread, and feel as natural as macOS's own privacy controls.

This document shows the patterns explored, with the approved design decision clearly marked. The approved model is a hybrid: Pattern C (independent checkboxes) for persistent defaults + mandatory Session Scope Review before any grant is created.

Sources: Apple HIG, About Face (Cooper), Don't Make Me Think (Krug), NN/g guidelines, Designing Interfaces (Tidwell)

The Core Problem

Users have N source folders. Two agents exist (Claude via Cowork, and Codex). For each folder, the user needs to decide: which agent(s) can see it? The original wireframe used a tri-state pill (Claude | Codex | Off) which was ambiguous — it looked like a segmented control (exclusive selection) but needed to support additive selection (both agents ON).

Key constraint: With only two agents, each source has just two independent binary questions ("Include for Claude?" and "Include for Codex?"). The UI must not hide the answer behind progressive disclosure when the answer is only two checkboxes deep.

Important: Claude and Codex can each have their own active session simultaneously, with separate materialized workspaces. The same source can appear in both sessions. If both agents modify the same file, each has its own copy — PromoteEngine handles conflict resolution at session end.

Approved Design: Pattern C + Mandatory Session Scope Review

Three-layer trust model
Layer 1 — Persistent defaults (Files sidebar, Pattern C): Independent checkboxes per source, per agent. Label: "Default access for new sessions." Changes affect only future sessions, never active grants. Both unchecked = off.

Layer 2 — Session Scope Review (Home tab, Pattern D-derived): Mandatory before any grant is created. Pre-populated from Layer 1 defaults for the selected agent. User can edit without mutating defaults. Includes email sensitivity, session notes mode, timeout, and preset. Footer shows exact scope summary. "Save as Defaults" is an explicit, separate action.

Layer 3 — Temporary session exceptions (Emails only, v1): Sensitivity-blocked emails can be added to the current session via "Add to this session" button. Exceptions expire when the session ends. No permanent per-email overrides in v1.

This mirrors Apple's privacy pattern: app-level defaults (Settings → Privacy), scoped permission prompts (Selected Photos / Allow Once), and temporary access that expires.

Email Sharing Model (Approved v1)

Emails have a different trust profile than files. The sensitivity filter (strict/moderate/open) acts as an automatic bulk filter — hiding banking, health, and 2FA emails. On top of that, individual emails can be added as temporary session exceptions — never permanently overridden in v1.

Key terminology: "visible this session" (not "shared"), "auto-hidden" (not "blocked"), "Add to this session" (not "Share"). All language scopes to the current session.

Approved: Sensitivity as hard floor + temporary session-only exceptions via "Add to this session"
Sensitivity Floor + Temporary Exceptions
The sensitivity level sets default visibility. Auto-hidden emails show why they were hidden (domain category badge). Users can add specific hidden emails to the current session only. Exceptions expire when the session ends — Apple's "Allow Once" pattern.

Why temporary-only (v1):
• Apple's "Allow Once": Scoped, explicit, self-cleaning. No accumulating list of forgotten decisions.
• Trust model stays explainable: "Moderate hides banking/health/2FA. You can add specific emails for this session only."
• Reason badges build trust: Users see WHY an email is hidden, not just that it is.
• Session History records everything: Which exceptions were granted, when, by whom — full audit trail.
The key UX insight: show the reason why an email is auto-hidden (banking, 2FA, health) — not just "hidden." This builds trust because the user understands the filter logic. Permanent per-email overrides are deferred to v2 if needed.

Why mandatory
About Face (Cooper) — "commensurate effort": The effort to confirm should match the consequence of the action. Starting a session that gives an AI agent access to your files and emails is a high-consequence action. A single "Start Session" button with a summary line is not commensurate. A full scope review with checkboxes IS.

Apple's permission pattern: When an app requests access to your Photos, Camera, or Location, macOS shows exactly what's being requested and lets you choose the scope (e.g., "Selected Photos" vs "All Photos"). Manifold does the same — "Selected Sources" vs "All Sources."

Three important behaviors:
1. Editing the scope review does NOT change persistent defaults — only the session being created.
2. "Save as Defaults" is explicit and separate — users must intentionally click it to persist changes.
3. The footer shows the exact grant boundary: file count, total size, email count. No summaries, no hand-waving.
